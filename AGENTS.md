# Agent Development Notes

## Environment

This project uses `uv` for dependency management. The lockfile is `uv.lock`.

```bash
# Sync dependencies (including dev tools)
uv sync --extra dev

# Run commands inside the managed venv
uv run python -m pytest tests/
uv run python -m ruff check src/ tests/
uv run python -m black --check src/ tests/
uv run python -m mypy src/cloud_robotics_sim
```

On Windows, the venv interpreter is at `.venv/Scripts/python.exe`. Avoid using the system Python or external virtual environments.

The `robomat` material library is an optional local sibling package (`../robomat`, not on PyPI) wired through `[tool.uv.sources]`. It lives in the `robomat` extra so that pip-based CI (`pip install -e ".[dev]"`) works; install it locally with `uv sync --extra dev --extra robomat`. All robomat imports are guarded and degrade to simulator defaults when absent.

## Genesis Version

The project pins `genesis-world==1.4.0` (deterministic CPU/GPU simulation, improved ill-conditioned mass-matrix robustness, islands support, and the scene/trajectory `gs replay` archive). Do not use Genesis 0.4.x APIs.
Use the compatibility helpers in `src/cloud_robotics_sim/utils/genesis_compat.py` for backend selection, light creation, and external force application (`apply_entity_force`, which wraps the 1.4.0 `RigidLink.apply_external_force` wrench API with a legacy `apply_force` fallback).

Genesis 1.4 gotchas surfaced during the W4 acceptance (2026-09-27, all fixed in-tree): backend wrappers expose `set_dofs_gains` but not `set_dofs_kp/kv`, and entities are unbuilt at spawn time — PD gains and asset-default qpos capture must happen at first `reset()`, not `spawn()`. Genesis' OMPL `plan_path` returns an **all-zeros trajectory on silent RRT failure** (`plan_with_fallback` guards against it). GPU-backed scenes return CUDA tensors from `get_pos/get_quat` — always convert via the `_to_numpy_f64` helper in `backends/genesis_backend.py`. Genesis merges fixed-joint chains at build time (panda's `panda_hand` disappears — EE link is `panda_link7`, and the merged finger collision bodies extend centimeters below the link7 origin, so descend goals need extra clearance).

## Vectorized Throughput Baseline

`core/vec_tasks.py::FrankaPickCubeVecTask` is the first real `VecTask` on the batched-scene path (`core/vectorized.py`, `scene.build(n_envs=...)`, rsl-rl-style tensor interface): franka pick-cube, 24-dim obs / 9-dim delta-joint-pos actions, matching `configs/tasks/pick_place_cube.yaml` semantics. `tools/bench_vec_throughput.py` measures steady-state steps/s + peak VRAM over a (device, n_envs) grid (build time excluded, OOM recorded not fatal). Gotchas encoded there: PD gains and asset-default qpos are applied at first `reset()` (entities unbuilt at spawn); raw Genesis entities expose `set_dofs_kp`/`set_dofs_kv` (the project's *backend wrappers* expose `set_dofs_gains` instead — different layer); batched getters return subset-width tensors, so reshape by `-1`, not `num_envs`; and `gs.init(backend=cuda)` sets torch's **default device to cuda** process-wide — any CPU-generator `torch.rand/randn` must pin `device="cpu"` explicitly (both `vec_tasks.py` and `bench_vec_throughput.py` encode this). Local baseline (GTX 1650 4GB, 2026-10-02): out of the box ~50 steps/s (20 ms/step) on CUDA flat from 1→256 envs — profiling showed `scene.step()` is 17 of those 20 ms; obs/control/reward tensor ops total only ~1.1 ms. Tuning at the same solver rate (dt 0.02×2 substeps → 0.01×1, plus `gs.init(performance_mode=True)`, exposed as `VecEnvConfig.performance_mode`; static-array mode, no runtime scene edits, determinism unaffected) reaches ~187 steps/s @ 256 envs at 0.7 GB VRAM (~3.7×). `bench_vec_throughput.py` flags: `--sim-dt/--substeps/--performance` plus solver-fidelity knobs `--solver-iters/--ls-iters/--noslip/--no-self-collision/--hibernation` (all mirrored on `VecEnvConfig`). Full data: `outputs/benchmarks/vec_throughput_20261002/`. Follow-ups: Madrona batched rendering (L2), rsl-rl training loop (not installed yet), datacenter-GPU re-measurement (the launch-bound regime may flip to kernel-bound there), host-side step fusion (~2 ms of getters/obs/reward per step).

2026-10-04 ManiSkill3 same-hardware rebench (`outputs/benchmarks/ms3_rebench_20261004/`): on this GTX 1650, ManiSkill3 3.0.1 (SAPIEN 3.0.3 GPU sim, PickCube-v1) runs **13–24 steps/s** — 4–9× *slower* than our batched pick-cube (88–119 steps/s) — and its throughput *degrades* as envs grow (45→77 ms/step from 1→256). Its sim+render path segfaults on this Windows box under both gpu (Vulkan) and cpu render backends, and its published `peak_vram` only counts torch allocations, not the PhysX/renderer pool — treat “30k FPS / 2-3× less VRAM” as high-end-GPU+Linux 口径. Gaps vs MS3 that remain real: per-env heterogeneous scenes (Genesis single-scene batching is structurally homogeneous; multi-process sharding stays the answer) and batched rendering (Madrona L2); Windows/低端机部署摩擦（PhysX DLL 手动装、cuda.dll 缺失、渲染段错误）明显站在本项目一边。

2026-10-04 follow-up measurement (`outputs/benchmarks/vec_throughput_20261004_ab/`, `outputs/benchmarks/profile_vec_step_20261004/`): torch.profiler shows the step is **launch/host-bound** on this card — wall ~7-12 ms/step vs ~2 ms CUDA-busy, with `kernel_noslip` alone 80% of the *busy* time at the project's then-default `noslip_iterations=5`. Because the GPU idles between launches, cutting kernel busy time barely moves wall-clock: the paired back-to-back A/B across 1/16/64/256 envs showed throughput **neutral** (±10% noise) after switching the default to `noslip_iterations=0` (Genesis' own default), while scene build/init got **1.5-3.5x faster** (fewer solver kernels to JIT per process — build dominates RL startup, so this is the real win). Newton `iterations=15`, `enable_self_collision=False`, `use_hibernation=True`: no reliable wall-clock win here, defaults kept (knobs remain exposed for datacenter-GPU re-measurement, where the regime may flip to kernel-bound). Measurement caveat: this desktop GPU drifts up to ±60% between batches 30 min apart — only back-to-back paired comparisons are trustworthy; cross-day absolute numbers are order-of-magnitude only (2026-10-02's 187 steps/s @ 256 envs vs 2026-10-04's ~119 on identical configs).

## WFC Chinese Home Scene Generator (wfc_scenes)

`plugins/scenes/wfc_scenes/` procedurally generates Chinese-apartment scenes with Wave Function Collapse, addressing the ReplicaCAD dataset gaps (Western lifestyle, few scenes). `core/wfc.py` is a generic solver (constraint propagation, minimum-entropy collapse, snapshot backtracking, preset cells for "at least one X" constraints, in-collapse per-tile count caps). `core/rules_cn.py` is the organized rule set: 10 everyday Chinese home modules (living/dining/kitchen/bedroom/study/entry/balcony/tea/bathroom/corridor) with edge sockets (`wall/open/counter/rail/door`), rotation-invariant interior compatibility, exterior boundary rules (only wall/counter/rail/door may face outside), and a global validator (exactly one entry with proper flow, kitchen adjacent to living/dining, balcony hosting, per-tile count caps). Rooms support alternate wall patterns (corner rooms). `assets/furniture_cn.py` builds furniture as data-driven primitive specs (Prim) consumed by two backends: `TrimeshBackend` (offline GLB/preview, no Genesis needed) and `GenesisBackend` (genesis-world 1.4 primitive morphs `Box/Cylinder/Sphere` + `gs.surfaces.Default(color=...)` — `gs.morphs.Mesh` no longer accepts in-memory trimesh in 1.4). `scene.py::ChineseHomeScene` turns seed → layout JSON (replayable) + ASCII map + top-down SVG + GLB + live Genesis scene (every furniture prim is its own rigid body; walls/floors fixed). Existence/flow rules are guaranteed by construction via preset cell pairs (entry↔flow host, kitchen→opening→dining/living, balcony→host) chosen per attempt by `build_presets`; acceptance is ~100% for 3x2–5x4 grids, degrading gracefully beyond 6x5.

Variable cell sizes (方案 2): `variable_size=True` (CLI `--variable`) draws independent column widths / row depths per attempt within `[min_cell, max_cell]` and raises them to the hosting tiles' `TileSpec.min_edge` (客厅 3.2 / 卧室 3.0 / 厨房 2.8 / 卫生间 2.2 ...), giving 厅大卧小卫小 plans. Layout carries `col_widths`/`row_heights` (JSON v2, v1 uniform files still load) and exposes geometry via `cell_center/cell_span/cell_half/edge_segment` — all structure/SVG/GLB/furniture placement derives from these. Furniture anchors to walls through `PrimBuilder.hx/hy` (counters/carpets/racks adapt length). ROTATION CONVENTION: tiles rotate clockwise (`rotated_sockets`, `ROT_ARROWS`) and `PrimBuilder._to_world` must stay clockwise too — flipping it breaks furniture-vs-socket alignment at rot 90/270 (this exact bug shipped once; the per-tile fit tests catch it). CLI: `python -m plugins.scenes.wfc_scenes --grid 4x3 --seed 42 --ascii --batch 8 --out-dir outputs/wfc_scenes`. Integration hook: `populate_genesis_scene(gs_scene, layout)` before `scene.build()`. Tests: `plugins/scenes/wfc_scenes/tests/` (44 offline tests; Genesis CPU smoke test auto-skips without genesis-world). NOTE: `counters_ok`/entry-flow presets depend on `neighbors_inside` returning `(direction, cell)` pairs — keep that contract when editing.

## ManiSkill ReplicaCAD Scene Dataset

`plugins/envs/maniskill` integrates ManiSkill's ReplicaCAD scene dataset (the `ReplicaCAD_SceneManipulation-v1` scenes used by XLerobot) mirrored on ModelScope as `jessy888/ManiSkill_replica_cad_dataset` (single ~289 MB `replica_cad_dataset.zip`, Apache-2.0). `genesis_maniskill/datasets/replicacad_assets.py` (same pattern as `robotwin/assets.py`) checks/downloads/extracts it on demand to `assets/maniskill/` (gitignored): `ensure_dataset()` / `list_scenes()` / `download_dataset()` plus a CLI (`python -m genesis_maniskill.datasets.replicacad_assets`). Env vars: `CRS_REPLICACAD_ASSETS` (root override), `CRS_REPLICACAD_AUTO_DOWNLOAD=0` (disable; missing dataset then raises `FileNotFoundError`). `scenes/replica_cad_scene.py::ReplicaCADSceneBuilder` ports ManiSkill's ReplicaCADSceneBuilder semantics (RotX(+90°) Y-up→Z-up conversion, habitat xyzw → Genesis wxyz quats, DYNAMIC objects use the pre-decomposed convex collision GLB as body mesh, STATIC objects as non-convex fixed meshes, articulated furniture from `urdf/<name>/<name>.urdf`, doors skipped by default, masses applied via `set_mass()` in `finalize()` after `scene.build()`). `envs/replica_cad_env.py::ReplicaCADEnv` is the gym wrapper (num_envs=1 only; `scene.build()` is deferred to `_setup_spaces` so robot/cameras join before compilation). Example: `python plugins/envs/maniskill/examples/replica_cad_scene.py --scene apt_0 --save-img`. NOTE (2026-10-04 rebench, `outputs/benchmarks/ms3_rebench_20261004/`): the num_envs=1 restriction is a conservative guard only (`build()` uses num_envs nowhere else; entities carry no envs_idx so a batched scene would replicate the apartment per env) — but a homogeneous-batching probe OOMed at 32 envs on a 4GB card (whole-apartment non-convex stage + ~100 objects/env) and single-scene apt_0 build (convex decomposition) did not finish within 15 min on that box, so unblocking the guard is the *small* part — build-time caching and per-GPU env-count caps are the real work. True per-env *different* scenes are impossible on Genesis' single-scene batch path (multi-process sharding remains the hetero answer). Note: the plugin's `datasets` subpackage uses absolute imports and is only importable under the top-level `genesis_maniskill` name with `plugins/envs/maniskill/core` on `sys.path` (as the plugin examples do); `scenes/replica_cad_scene.py` therefore imports it lazily.

## Articulation Asset Auto-Annotation (articulation_gen)

`plugins/predictors/articulation_gen/` automatically annotates articulated furniture assets (drawer slides / cabinet-door hinges) into URDF-ready joint specs, targeting the same URDF articulation loading path as the ManiSkill ReplicaCAD plugin above. Three input paths: named-node GLB/USD (offline, zero inference deps — node names map to semantic kinds via substring hints), YOLO+SAM image back-projection (`ultralytics`/`sam2` guarded optional deps; public checkpoints don't cover drawer/door classes so a fine-tuned YOLO26-family model is expected), and pre-segmented part vertices (PartNet-style labels). The core (`core/estimate.py`) is a pure-numpy geometric estimator: PCA-OBB base/face fitting (proud-face criterion), prismatic axis from outer-face normal with escape-probe direction sign, revolute hinge chosen by collision-free sweep over both vertical edges, confidence = planarity × free-motion fraction, and a review queue (`batch_annotate` writes `review.jsonl`) instead of silently accepting low-confidence estimates. `core/verify.py` adds the optional Genesis closed-loop verifier (`GenesisVerifier`, lazy once-per-process `gs.init`): the exported URDF is loaded via `gs.morphs.URDF(fixed=True)`, each joint is ramped open-loop to its limit and judged on tracking error, finiteness, and an explicit geometric penetration check (child-link collision-box corners vs base AABB in world frame — adjacent links have no self-collision in Genesis by default, so mirrored-hinge-side errors only show up here); failures are demoted to the review queue with sim readings, and verifier exceptions quarantine the asset without aborting the batch (`sim_rejected` counted separately). `result_to_urdf` emits revolute/prismatic joints with world-frame axes (rpy=0 convention) and placeholder masses — call `set_mass()` after `scene.build()` as in ReplicaCAD. Only vertical hinges and straight slides are supported; lids/horizontal axes land in the review queue. Tests: `plugins/predictors/articulation_gen/tests/` (18 tests; `test_articulation_gen.py` is numpy+trimesh offline, `test_genesis_verification.py` needs genesis and auto-skips without it).

## 3D Asset Generation APIs (asset_gen)

`src/cloud_robotics_sim/asset_gen/` is a stdlib-only (`urllib.request`) client layer for commercial text/image-to-3D services, with a unified `GenerationRequest`/`GenerationResult` model, a provider registry (`register_provider`/`get_provider`/`list_providers`), shared async-task polling (`base.poll_task`), and a facade (`AssetGenClient.submit_text`/`generate_image`/`generate`) that downloads the GLB plus a `.json` provenance file into a staging dir ready for `scripts/expand_object_library.py`. Built-in providers: `tripo` (Tripo AI V2 OpenAPI; V2 EOL 2026-11-01, migrate via `TRIPO_BASE_URL`), `meshy` (Meshy v2 text-to-3d / v1 image-to-3d), `hunyuan3d` (Tencent Cloud `ai3d` service, API version 2025-05-13, full TC3-HMAC-SHA256 signing implemented in-module; pro jobs by default, `extra={"rapid": True}` for the rapid tier), and `rodin` (Hyper3D v2 multipart submit + status/download). Credentials come from env vars (`MESHY_API_KEY`, `TRIPO_API_KEY`, `RODIN_API_KEY`, `TENCENTCLOUD_SECRET_ID`/`TENCENTCLOUD_SECRET_KEY`, optional `HY3D_REGION`); a project `.env` is loaded by the CLI when `python-dotenv` is installed. CLI: `python -m cloud_robotics_sim.asset_gen providers|text|image`. Tests in `tests/asset_gen/` mock all HTTP and pin the TC3 signature against Tencent's official worked example.

## Grid Field Solver Plugins (thermal / joule_heating / acoustics)

`plugins/solvers/` holds three structurally identical grid-based field solver plugins injected into a `gs.Scene` before `scene.build()` (`install(scene, options)` sets `scene.sim.<name>_solver` and appends to `scene.sim._solvers`): **thermal** (explicit FTCS conduction with energy-conserving entity coupling), **joule_heating** (Jacobi electric potential → `Q = σ|∇V|²`, optional `couple_to_thermal=True` injection), and **acoustics** (second-order leapfrog linear wave equation; absorbing sponge layers / Dirichlet p=0 / Neumann rigid boundaries; `add_source()` monopoles, `add_body()` one-way vibro-acoustic velocity injection `ρ·dv_z/dt`, `add_probe()` virtual microphones with Hann-FFT `spectrum()`/rms `spl()` post-processing at 2×10⁻⁵ Pa; CFL `c·dt/dx ≤ 1/√dim`). All three were adapted to genesis-world 1.4.0 quirks: `Solver` no longer mixes in `TimeBasedMixin` (each solver sets `_substep_dt = options.dt` in `build()`), `install()` defaults `dt` from `scene._sim.dt`, and quadrants 1.3 rejects field aliases inside kernels (`x = self._field` then `x[i]`) and cannot autodiff host-precomputed constant fields (material params must be inlined into kernels, cf. `joule_heating._heat_step_*`). Source-coupling backward paths remain skipped pending the upstream quadrants AD fixes (see `scripts/quadrants_issue_thermal_source_autodiff.md`). Tests live in each plugin's `tests/` (CPU-only; run per plugin — each module calls `gs.init`), examples in `examples/basic_usage.py`.

`plugins/solvers/cfd_coupling/` is dual-mode like the others: `install(scene, options)` / `install_pipe` / `install_cfd` (`solver.py`) inject `CoupledCFDSolver` / `PipeSolver` / `CFDSolver` into `scene.sim._solvers` before `scene.build()` (one genesis substep = one coupling macro step; `_substep_dt` from `sim.substep_dt` in `build()`; no-op `process_input`/`save_ckpt`/grad hooks on `_PluginSolverBase`; dummy entity marker for `Simulator.reset()` via `get_state`/`set_state`). The CFD core has two numerically-equivalent, duck-type-compatible backends selected by `CoupledSolverOptions.backend` (`"quadrants"` default / `"torch"` fallback / `"auto"`): `core/cfd3d_qd.py` (`@qd.kernel` Taichi kernels like the other solver plugins — predictor/diffusion/divergence/projection/temperature all on-field, honouring quadrants 1.3 no-alias and no-return-in-runtime-if rules; latency ~1.8 ms/step median vs ~7.5 ms/step for the torch core at 20x10x10 on CPU, via two fused kernel launches per step, in-kernel `-1/dt` divergence pre-scaling, zero-copy `qd_to_torch` transfers into the cached f64 sparse LU, and a two-frame temperature buffer) and `core/cfd3d.py` (pure PyTorch, importable without genesis). Both share the same host-side pressure Poisson assembly `build_poisson_csr` (cached sparse LU ≤30k cells, scipy CG otherwise — a direct solve costs ~1 ms and keeps both backends at the same latency). The 1D MOC pipe (`pipe1d.py`, NumPy) and the macro-step coupler (`coupler.py`: 1D sub-cycling, Gauss-Seidel fixed-point interface iteration, ms-scale valve events) are backend-agnostic. Built for the COMAC "1D-3D CFD coupling" competition problem; validated by Joukowsky water hammer, lid-driven cavity, mass conservation, backpressure response, fixed-point convergence, qd-vs-torch parity/latency and gs.Scene lifecycle tests in its `tests/` (`test_coupling.py` genesis-free, `test_genesis_integration.py` needs genesis — one `gs.init` per process, keep both files' genesis tests in the same module). The pressure solve is specific pressure p/ρ: heads are p/g, not p/(ρg). Autodiff hooks are no-ops on both backends. Both 3D backends also support immersed-solid obstacles (`set_solid_mask` / `add_obstacle(file|trimesh|entity|part-list, position=, rotation_euler=, scale=)` via `core/obstacles.py` rasterization; no-slip walls + Neumann Poisson boundaries, torch/qd numerically identical): CATIA models come in as STL or STEP — `.stp/.step` assemblies parse directly through the optional `cad` extra (cadquery/OpenCASCADE, one mesh per solid, `mask_from_step`/`meshes_from_step`); CATPart/CATProduct are proprietary and must be exported. `add_obstacle(..., track=pose_fn)` re-rasterizes moving obstacles every substep (one-way coupling); `obstacle_forces()` integrates pressure + wall-shear loads per obstacle (N, world axes). Obstacles must stay clear of the x=0/x=Lx faces.

## Sparse Voxel Module (vdb)

`src/cloud_robotics_sim/vdb/` is a dual-backend block-sparse volume module (factory `create_volume(backend="torch"|"xuvdb"|"auto")`, mirroring the cfd_coupling backend-option semantics). `core/vdb_torch.py::TorchSparseVolume` is a torch-only prototype with a fixed logical domain (`nx×ny×nz`, must be a multiple of `block_size`) and dynamic block topology; `core/vdb_xuvdb.py::XuvdbVolume` wraps the optional `xuvdb` PyPI package (太虚: quadrants-based editable sparse voxel volumes — unbounded domain, SDF/CSG `stamp_sphere` min-union, DDA `ray_surface_hit`, particle splat, native `.xuvdb` and OpenVDB `.vdb` interop without pyopenvdb). The `xuvdb` extra (`pip install cloud-robotics-sim[xuvdb]`; pure-python wheel, deps numpy+quadrants — the Aliyun mirror does NOT carry it, so pyproject pins it to an `explicit = true` pypi-org `[[tool.uv.index]]` via `[tool.uv.sources]`; named indexes take precedence over the default index in uv, without `explicit = true` a re-lock flips every package to pypi.org) is guarded like `cad`: `vdb_xuvdb.py` never imports xuvdb at module level, so `import cloud_robotics_sim.vdb` is always safe and only instantiating the backend raises a naming ImportError. torch↔xuvdb conversion (`to_xuvdb`/`from_xuvdb`) goes through a dense numpy round-trip (xuvdb `to_dense` returns the tight ACTIVE bbox `(dense, ijk_min)`, possibly negative-origin; `from_xuvdb` rounds the torch domain up to a block multiple); also note `xuvdb.read_vdb` returns a *list* of grids. Tests: `tests/vdb/` (torch tests run everywhere; xuvdb tests skip via `tests/optional_deps.py::xuvdb_only` since CI installs only `.[dev]`).

## Nozzle Exhaust 1D-3D Coupling (nozzle_coupling)

`plugins/solvers/nozzle_coupling/` couples a quasi-1D converging-diverging rocket nozzle to a 3D weakly-compressible exhaust plenum, targeting the published engine/nozzle assets of open-source rocket projects (e.g. github.com/webwizarding/MANPADS — which per its SAFETY.md publishes no motor data; all plugin inputs are user parameters, no propellant/motor data is included). Dual-mode like cfd_coupling: genesis-free cores (`core/nozzle1d.py` curve-driven chamber + Sutton-style two-phase mixture rules and velocity-lag factor, regime selection by returned backpressure: supersonic / normal-shock-in-divergent (shock-area-ratio bisection, lip-clamped below the lip-shock pressure) / subsonic / blocked; `core/jet3d.py` anelastic low-Mach 3D solver — diagnostic EOS rho=p_amb/(R_mix*T), thermal-expansion divergence target from the energy equation, variable-coefficient projection solved by CG with a cached constant-coefficient sparse-LU preconditioner, mass-flux inlet BC, runtime `set_outlet_patch` throttling; `core/coupler.py` macro-step coordinator, trapezoidal window means, Gauss-Seidel fixed point) + genesis wrappers (`install`/`install_nozzle`/`install_jet`, one substep = one macro step). Key numerics lessons: the quasi-steady nozzle is infinitely stiff (mdot jumps to zero at p_back>=p_c), so the interface MUST be slew-limited on both directions (`backpressure_max_rate_pa_s`, `inlet_mdot_slew_kg_s2`) or it limit-cycles blocked<->choked; hot supersonic jets are momentum-dominated and pressure-matched at the exit plane, so the strongest 3D->1D backpressure signals come from cold / low-pressure-ratio configs; the 3D step is CFL-limited by the exit jet velocity (u_e*dt/h ≲ 0.5). Tests in `tests/` (1D closed forms, jet mass/projection/backpressure, end-to-end throttle event, deterministic interface plumbing, gs.Scene lifecycle; in `scripts/plugin_test_dirs.txt`).

## Agent Runtime (skill-based)

`src/cloud_robotics_sim/runtime/skills.py` is the agent-facing skill layer: `Skill` (name + description + JSON-Schema parameters + handler), `SkillRegistry` (validate/dispatch), `TaskExecutor` (executes skills, resolves natural-language goals deterministically via token matching with per-skill parameter extractors, e.g. patent IDs, and records every run), and `ReplayBuffer` (in-memory + optional JSONL). Built-in skills: `run_patent`, `list_patents`, `list_scenes/robots/tasks`, `submit_sim_task`. Register custom skills with `@register_skill`. `runtime/agent_hub.py` exposes the same surface as zero-dependency MCP-style tools (`SimHub`, `list_tools`/`call_tool`, optional `serve_stdio` via the `mcp` package) mirroring `devices/mcp_adapter.py`; the CLI `cloud-robotics-sim agent --goal/--skill/--param/--list-skills` is a thin wrapper. `queue_worker` delegates patent execution to `skills.run_patent_task` so sync (skill) and async (KEDA queue) paths share one implementation. The CLI (`cloud-robotics_sim/__main__.py`, argparse) also provides a `plugins` subcommand group (`list`/`info`/`config`) on top of `core/plugin_manager.py` + `core/plugin_config.py` for plugin discovery, README-usage display, and per-plugin user config overrides (`~/.cloud-robotics-sim/plugins/<name>.yaml`, override dir with `CRS_PLUGIN_CONFIG_DIR`).

## Kubernetes Deployment

`deploy/kubernetes/` contains native YAML manifests (no Helm) for queue-based autoscaling: a Redis queue Deployment, CPU/GPU sim-worker Deployments, and KEDA `ScaledObject`s that scale each worker tier from 0 based on its Redis list length (`sim-tasks-cpu` / `sim-tasks-gpu` are separate queues so one queue never scales both tiers). The worker entry point is `cloud-robotics-sim worker` (`src/cloud_robotics_sim/runtime/queue_worker.py`), which consumes JSON task specs via `BRPOP` and appends results to the `sim-results` Redis list. Task types are registered in `_TASK_HANDLERS` (currently `patent`). The `redis` client is an optional dependency behind the `k8s` extra (`pip install cloud-robotics-sim[k8s]`); it is never imported at package top level. `scripts/k8s_submit_task.py` pushes tasks onto a queue. See `docs/guides/kubernetes.md` for the full guide.

## Meshy T2 Module

`src/cloud_robotics_sim/meshy_t2/` is a pure-PyTorch reproduction of the Meshy T2 paper (arXiv:2607.28675; official code unreleased): vertex-set Mesh VAE (spacetime edge logits + halfedge successor faces with NULL extension + Sinkhorn), Voxel VAE, and a two-stage Rectified-Flow cascade (voxel scaffold flow -> per-vertex latent flow with Sobol-OT 3D RoPE positions, existence channel and vertex-count conditioning). It is torch/trimesh/scipy-only (no Genesis import). Model defaults match the paper; `*.tiny()` configs run on CPU. Train with `python -m cloud_robotics_sim.meshy_t2 train {voxel-vae,mesh-vae,voxel-flow,mesh-flow} --tiny`, generate with `... generate image.png --num-faces 4000`; tests live in `tests/meshy_t2/`. mypy `warn_return_any` is disabled for this module in `pyproject.toml` (torch stubs return `Any` pervasively).

## Simulated Devices Module (MHS-style)

`src/cloud_robotics_sim/devices/` is an MHS-inspired device abstraction layer: every simulated device exposes typed read/write primitives (`SimDevice.read`/`write`, validated against `WritePrimitive` safety bounds, raising `SafetyViolationError`), carries `compliance` GB-standard metadata, and generates an agent-facing reference file via `reference_file_yaml()` from the standards catalogs in `data/standards/` (`robot_standards_catalog.yaml`, `lab_equipment_standards.yaml`). Fault models in `faults.py` (`SensorDrift`, `SensorStuck`, `RelayStuckClosed`, `InterlockBypass`) support safety-evaluation scenarios. Devices: `MuffleFurnace` (lumped thermal, door interlock + latching over-temperature cutout per GB 5959.4-2008), `UniversalTestingMachine` (piecewise stress-strain specimen + frame compliance solved by bisection; GB/T 16491-2022 overload/fracture auto-stop, GB/T 228.1-2021 extensometer handling), `SharpaHandDevice` (Genesis-backed, vendored URDF from `plugins/do_as_i_do/assets/sharpa-urdf-usd-xml-main/` — `package://` mesh paths are rewritten to absolute paths before loading; fingertip links are merged into `*_DP` distal-phalanx links by Genesis; PFL force guard per GB/T 36008-2018). `mcp_adapter.py` exposes a `DeviceHub` over MCP-style tools (`list_tools`/`call_tool`, zero-dependency; `serve_stdio` needs the optional `mcp` package). Register new devices in `devices/__init__.py` `DEVICE_TYPES`; tests live in `tests/devices/` (Genesis hand tests take ~30s on CPU).

## Classic Patents Module

`src/cloud_robotics_sim/patents/` ports the 22 interactive patent demonstrators from classic-patents.com into Genesis. The Wright Flyer (`US821393`), Edison's Electric-Lamp (`US223898`, lumped electro-thermal model: negative-TCR carbon resistance, Stefan-Boltzmann radiation, Arrhenius filament wear with vacuum-dependent oxidation, Planck/photopic luminous flux) and Tesla's Electro-Magnetic Motor (`US381968`, double-revolving-field induction model: phase-offset-dependent forward/backward field decomposition, Kloss torque-slip curve, lumped rotor mechanics) and Morse's Electro-Magnetic Telegraph (`US1647`, RL line charging, Maxwell armature attraction with pull-in/drop-out hysteresis, key-timing Morse decoder), Tesla's Electrical Transformer (`US593138`, coupled resonant LC circuits integrated exactly with the matrix exponential, spark-gap fire/quench cycle, tuning-dependent voltage gain) and Goddard's Rocket Apparatus (`US1155986`, variable-mass Tsiolkovsky flight with exponential-atmosphere drag, hold-down clamps, hot staging and a ballistically falling booster), Fermi & Szilard's Neutronic Reactor (`US2708656`, six-group delayed-neutron point kinetics with negative-temperature self-regulation and scram tail), Bell's Telephone (`US174465`, magneto transmitter/receiver pair: diaphragm-driven variable-reluctance EMF over an RL line), Farnsworth's Television System (`US1773980`, electron gun with magnetic deflection raster scanning), Howe's Sewing Machine (`US4750`, slider-crank needle bar with shuttle lockstitch timing and a thread-tension stitch/miss/break window) and Spencer's Microwave Oven (`US2495429`, standing-wave cavity heating of a 3x3 food grid with boiling plateau and turntable uniformity) are fully implemented; the other 11 patents ship as runnable stubs under `patents/sims/` registered via `@register_patent`. Metadata lives in `patents/data/patents_catalog.yaml`; run simulations with `uv run python -m cloud_robotics_sim patents --list` / `--run US821393`. In genesis-world 1.4.0, rigid bodies expose `control_dofs_force([Fx,Fy,Fz,Tx,Ty,Tz])` (world frame) instead of `apply_force` (external forces go through `RigidLink.apply_external_force`/`apply_external_wrench` — use the `apply_entity_force` compat helper), use `rho=` (not `density=`) in `gs.materials.Rigid`, and cameras must be added before `scene.build()`.

The Wright Flyer visual is the Smithsonian NASM CC0 scan (`assets/patents/wright_flyer/smithsonian-nasm-1903-flyer.stl`, ~14 MB, gitignored; download from `https://cdn.jsdelivr.net/gh/Dicklesworthstone/classic-patents.com@main/public/models/wright-flyer/smithsonian-nasm-1903-flyer.cc0.stl` — jsDelivr mirror works where raw.githubusercontent.com stalls). Missing mesh falls back to a box. Genesis gotchas hit here: mesh rigid bodies get their mass from the *convex-decomposed* collision volume (or the convex hull for non-watertight scans with `collision=False`), which inflated the 340 kg Flyer to 8.4–17.4 t — fix by calling `entity.set_mass()` after `scene.build()`, which scales the inertia tensor by the same ratio. CoACD decomposition of the 297k-face STL takes ~2.5 min once, then is cached in `~/.cache/genesis/cvx/`. Angular velocity comes from `entity.get_ang()` (world frame) — `get_angular_velocity()` does not exist, so `hasattr` guards around it silently disable any damping that relies on it.
